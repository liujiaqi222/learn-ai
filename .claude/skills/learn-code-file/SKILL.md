# Learn Code File

把一个代码文件改造成学习材料：补注释、画流程图、理顺结构、保留功能、跑通验证。

## 参数：指定已知 / 未知（按需）

用户会告诉你哪些已懂、哪些不懂，**按这个调整注释深度，别解释他已经会的**。

**用户可能这样说**（自然语言，灵活识别）：
- "我已经懂 spawn 了" / "args 我会" / "跳过基础的"  → 已懂，轻处理
- "重点讲 stdio" / "事件循环不懂" / "详细说 xxx"    → 不懂，深挖

**也可显式传参**（调用 skill 时）：

```
/learn-code-file <文件路径>  已懂: spawn, split  不懂: stdio, close事件
```

**处理规则**：

| 用户标记 | 注释深度 |
|---------|---------|
| 已懂 | 一行带过或不加注释，不展开原理 |
| 不懂 | 重点展开：多写原理 + 对比写法 + 流程图 + 举例 |
| 没提到 | 按默认新手友好处理 |

> 没收到任何已知/未知提示时，全部按新手友好处理（默认行为，跟初次使用一样）。

## Quick start

1. 读目标文件 + 项目上下文 + **用户的已知/未知提示**（见「参数」）
2. 重写文件：按已知/未知调整每段注释深度，补图、分段、修格式
3. 用项目的方式跑一遍，确认功能没变
4. 用表格汇报改了啥 + 点出 2-3 个关键学习点

## Workflows

### 必须遵守的原则

- **保留功能**：行为完全不变，只是更可读（这是底线）
- **写「为什么」而非「是什么」**：注释解释意图、原理、坑点，不复述代码
- **按需调整深度**：用户说"已懂"的一笔带过，说"不懂"的重点深挖（见「参数」）
- **新手友好**：没特别说明时默认读者不懂，关键概念要展开讲
- **匹配项目风格**：分号 / 缩进 / 命名跟同项目其他文件一致（先读相邻文件判断）

### 注释怎么写

| 场景 | 做法 |
|------|------|
| 复杂概念 / 数据流 | 画 ASCII 流程图（`┌─└│▼►` 框线 + 箭头），放文件头或概念上方 |
| 长文件 | 用 `// ─────────` 分隔线分段，每段配小标题（1. 准备 / 2. 执行 / 3. 监听） |
| 每个选项 / 参数 | 注释讲它的作用 + 不写会怎样（对比写法） |
| 文件头 | 一段总览：这文件干啥 + 核心步骤 |

### 流程图示例

```
 *   spawn(cmd, args, options)        ← 启动子进程，返回 ↓
 *        ┌──────────────┐
 *        │  child 对象   │
 *        └──────────────┘
 *         │      │      │
 *         ▼      ▼      ▼
 *      stdout  stderr  stdin   ← 3 个流（每个都是 EventEmitter）
```

### 完整步骤

1. **读上下文**：目标文件 + 相邻文件 + 配置文件 + **用户的已知/未知提示**，判断风格、运行方式、每段注释深度
2. **重写**：先按已知/未知分配每段深度，再分段 → 补注释 → 画图 → 修格式（一次性 Write 整个文件）
3. **验证**：跑一遍（`bun run` / `npx tsx` / `npm test` / 项目脚本），确认输出和原来一致
4. **汇报**：
   - 表格列出改了啥（结构 / 注释 / 格式 / 文件头）
   - 点出 2-3 个关键学习点（新手向，讲原理）
   - 给一个「下一步可试」的练习建议（改个参数 / 换个玩法看变化）

## 边界情况

- 文件很大（>200 行）：只改造用户指定的核心部分，其余保持原样
- 配置文件（JSON / YAML）：别破坏格式，用独立 .md 或允许的字段说明
- 改完跑不通：**先回退保证功能**，再说明哪里改出了问题
- 用户只想"解释"不想改文件：就只在对话里讲，不动文件（看用户原话判断）
