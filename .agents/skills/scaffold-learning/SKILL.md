# Scaffold Learning

为 `~/code/learn-ai` 创建以“理解机制 → 亲手实操 → 独立测评 → 最后对照”为主线的学习目录。
仓库使用 **TypeScript + Bun**。

## 先确定任务范围

- **新建练习**：创建下述三件套、必要配置、AI 示例和预写测试。
- **优化现有章节**：读取当前内容与学习者代码，按请求修改文章或练习；保留无关文件和已有作答。只改 explainer 时，不要求顺带重建 problem 或 solution。
- **讨论方向**：先分析资料、范围和文章组织方式；用户要求先讨论时，讨论阶段不落盘。

## 学习主线与参考资料

| 来源 | 作用 | 读取方式 |
|---|---|---|
| `~/playground/wechat-local-reading/` | 决定学习推进顺序、本节要解决的问题、实操场景及下一节衔接 | 从 `agent-fullstack-album/album-index.md` 或索引元数据定位当前正文；目录可能保留旧编号，按索引和标题确认 |
| [LangChain 官方文档](https://docs.langchain.com/) | 核对框架职责、当前推荐 API、参数和行为 | 优先查 JavaScript / TypeScript 文档，并对照练习实际安装版本的类型与实现 |
| [AI Agent Book](https://github.com/bojieli/ai-agent-book) | 参考专业术语、概念边界和工程原理 | 先查相关正文；本地副本为 `~/playground/content-creation/tutorials/ai-agent/source/ai-agent-book/`，使用前核对来源与所需版本 |
| 仓库中的 LangChain / LangGraph / Deep Agents skills | 帮助选择相关文档和核对实现方式 | 按当前主题读取；技术结论回到官方文档及实际依赖核验 |

课程决定“现在学什么”，官网和参考书帮助“讲准确、讲明白”。按本节问题选取资料，不按参考书目录另排课程，也不把视频稿当作概念的权威来源。

这些资料分工用于备课。面向读者的文章直接进入主题，省略 local-reading、本地归档路径及备课过程说明；参考资料保留相关官网页面和参考书章节。

一篇 explainer 围绕一个完整的学习问题展开；紧密相关的课程文章可以合并。只展开当前问题所需的概念，其余在出现处简要界定，留待对应章节深入。

技术冲突按内容处理：API 以官网和实际依赖为准，概念对照参考书及官方定义。正文直接介绍当前使用的 API；除非用户要求，省略旧 API 和迁移历史。Python、Node.js 或其他运行时的材料应转成适合本仓库的 TypeScript + Bun 写法，并解释影响运行的差异。

## 核心边界

三个目录按作者和用途划分：

| 目录 | 谁写 | 用途 |
|---|---|---|
| `explainer/` | AI | 可独立阅读的学习文章，以及 AI 生成的完整参考代码 |
| `solution/` | 学习者 | 跟着原始材料亲手完成的整体实操 |
| `problem/` | AI 出题，学习者作答 | 按独立能力拆分的 TODO 与预写测试 |

必须遵守：

- **禁止在 `solution/` 生成完整代码。**
- 新建时只为 `solution/` 写 `readme.md`，说明实操目标和建议文件名。
- 不覆盖、补全或重写学习者已有的 `solution/` 代码，除非用户明确要求修改。
- AI 完整实现文件放在 `explainer/examples/`，并标明“AI 参考代码”；正文保留理解机制所需的关键代码。
- `problem/` 的测试先于学习者实现存在；TODO 未完成时测试失败是正常状态。

## 目录结构

```text
XX-Topic/projects/NN-exercise-name/
├── explainer/
│   ├── readme.md
│   └── examples/
│       └── ...               # AI 完整示例
├── solution/
│   └── readme.md             # 学习者实操区，不放 AI 代码
├── problem/
│   ├── readme.md             # 题目索引
│   ├── 01-one-capability/
│   │   ├── readme.md
│   │   ├── index.ts          # TODO 起手架
│   │   └── index.test.ts     # 预写行为测试
│   └── 02-next-capability/
└── package.json
```

- Topic：`XX-Topic/`，例如 `01-Tools`。
- Exercise：`XX-Topic/projects/NN-exercise-name/`。
- 编号保持两位数；名称使用小写 dash-case。
- 共享的 `package.json`、`tsconfig.json`、`.env.example` 放在练习根目录。

## 如何拆 Problem

按“能独立证明已经掌握的能力”拆题，不按文章段落或单个 API 机械拆分。

好的题目：

- 能用一句话描述可观察结果。
- 不依赖前一道题，能单独运行。
- 一题只保留一个主要学习目标。
- 起手架只提供无关样板和必要数据，不泄露核心答案。

如果两个知识点只有组合后才有意义，可以合成一道集成题；不要为了数量制造碎题。

## 测试规则

每道题必须有测试，并在写 TODO 起手架时一起生成。

- 测**对外行为**，不要搜索源码或限定必须使用某种写法。
- 优先使用确定性的本地数据、fake、in-memory transport。
- 默认不调用真实模型、不消耗 API key、不访问不稳定的外部服务。
- 至少覆盖主路径和一个重要边界条件。
- 测试名称要直接表达能力，例如“能发现并调用 query_user”。
- 使用 `bun test problem/01-example` 单独运行。
- 测试本身必须能够加载；TODO 未完成时应因断言不满足而失败，而不是语法错误。

## Explainer 规则

`explainer/readme.md` 是一篇能独立阅读和复习的技术文章。读者懂基本 TypeScript，但不必打开原课程、示例文件、solution 或其他章节，才能理解本节机制。

### 组织方式

围绕一个贯穿全文的具体任务推进论证，例如“让模型读取文件并解释内容”。通常需要讲清：

1. 任务为什么需要这项能力，以及读完应能解释或实现什么。
2. 核心角色分别负责什么，哪些信息和操作属于哪个角色。
3. 一次完整运行中，输入、关键中间数据、状态变化和输出如何衔接。
4. 核心 API 如何实现上述机制，以及每段关键代码为什么放在这里。
5. 多轮、异常或边界条件会怎样改变运行，当前示例能保证什么。
6. 如何运行示例、怎样自测理解，以及本节如何接到课程下一步。

根据主题调整段落，不机械套固定标题。API 随机制引入；定义、例子和适用边界放在相邻位置。区分普遍机制、协议要求和本示例的实现选择，避免把简化模型讲成普遍定律。

### 代码与图示

- 正文展示足够的关键代码和具体中间数据，让读者能推演运行，并重新写出核心机制。
- 核心实现采用直观写法，例如工具调用用 `while` 表达“仍有调用就继续”；与本节机制无关的工程控制在边界说明中交代，避免挤占主线。
- 每个代码块说明它解决哪一步；片段有省略时写明前提，完整示例文件负责实际运行。
- 优先用消息轨迹、数据流图或小型对照表说明时序和职责。图中的名字、字段与正文代码一致。
- 完整实现放在 `explainer/examples/`；文章中的仓库、目录和文件链接使用 `https://github.com/liujiaqi222/learn-ai` 对应地址。运行说明给出下载仓库和进入章节目录的方法，代码中的文件路径按运行所需保留相对路径。
- 示例输出标明是示意还是实际运行记录。模型自由生成的措辞不写成固定验收结果。

### 术语与复习

- 重要术语首次出现时采用“中文名（英文名）”，之后保持一致，并在使用处解释含义。
- 比喻之后给出精确定义；框架、协议、设计模式和具体实现分别说明。
- 结尾提供核心机制速记，以及针对因果、时序和故障推演的自测题，附简短解析。自测可以帮助复习，但 problem 的核心实现答案仍留给学习者。
- 文末列出相关官网页面、参考书具体章节及 API 核验日期。文中依赖资料的关键结论在附近给链接；参考链接用于核验和延伸阅读。

### 完成标准

交付前逐项检查：

- 单独阅读文章，能否说明问题、角色、全过程和停止条件？
- 能否依据正文重新写出核心机制，而非只能辨认 API 名称？
- 关键数据有没有具体例子，示例代码和轨迹是否一致？
- 是否存在必须跳转代码才能补全的解释，或重复而分散的论述？
- 是否把模型行为、实现假设或演示结果误写成必然保证？
- 文件链接、运行目录、环境变量和命令是否与实际文件一致？

结构校验只能证明目录完整，文章还需人工通读确认以上标准。

## Solution 规则

`solution/readme.md` 只写：

- 原始学习材料来源。
- 本次整体实操要完成什么。
- 建议创建哪些文件、如何运行。
- 明确“代码由学习者完成，AI 脚手架不会生成或覆盖”。

`solution/` 没有 `.ts` 文件是合法的，表示学习者尚未开始。

## 工作流

1. 确定是新建、修改还是讨论；读取工作区改动、学习计划、对应课程正文和相邻练习，明确本节问题与范围。
2. 查相关官网和参考书，核对实际依赖，提取需要掌握的机制、术语与可观察能力。
3. 编写或修订独立文章和必要的 AI 示例，按 Explainer 完成标准通读检查。
4. 新建练习时，创建三件套与共享配置，为独立能力编写 TODO 和行为测试，只为 solution 创建说明。修改现有章节时，只做请求范围内的调整。
5. 有新增依赖时安装；仅修改文章时不顺带升级依赖或改配置。
6. 涉及目录结构时，在仓库根目录运行结构校验：

   ```bash
   bun .agents/skills/scaffold-learning/check-exercises.ts
   ```

7. 对新增或修改的 AI 示例运行类型检查和确定性的本地验证；模型调用默认不消耗 API key。区分离线验证与真实模型运行。涉及 problem 时，确认测试可加载，并说明未完成 TODO 导致的预期失败。
8. 汇报文章与规范的变化、完成的验证及实际限制，不自动 commit；只有用户明确要求时才提交。
